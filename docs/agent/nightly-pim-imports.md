# Proposed production PIM import

This is an operational proposal for discussion with the PIM owner, not an implemented feature or a requirement for the take-home seed. The current assignment excludes authentication and limits application write flows to reviews; a future administrative interface and alerts require a separate scope and authorization design.

1. Agree a versioned contract with the PIM owner: full-snapshot semantics, SKU identity and status meanings, required fields, export schedule and deadline, ownership, and how corrections are delivered. Include a unique export ID, snapshot generation time, row count and checksum in a manifest or equivalent completion signal. Confirm the mechanism and guarantees with the PIM team; the provided example has none of these guarantees.
2. Receive the completed export through an agreed authenticated, access-controlled channel, such as company-managed object storage. Retain the original file and metadata under a suitable retention policy. Trigger a scheduled or file-arrival job once completeness is established; alert if the expected export is missing or late. Do not assume a particular cloud vendor or build a scheduler for the take-home.
3. Validate the contract, checksum, row count and basic quality before publishing. Report duplicate IDs and field-level problems with SKU and source row numbers. Agree thresholds with the PM, including what should block publication and what may proceed with warnings; a valid-looking partial snapshot can otherwise remove many products from discovery. Retain failed inputs and diagnostics for investigation. AWS describes validating uploads and routing failures for notification; Google recommends preserving failed records for inspection ([AWS pattern](https://docs.aws.amazon.com/prescriptive-guidance/latest/patterns/orchestrate-an-etl-pipeline-with-validation-transformation-and-partitioning-using-aws-step-functions.html), [Google guidance](https://docs.cloud.google.com/dataflow/docs/guides/pipeline-best-practices)).
4. Stage and apply one accepted snapshot atomically, retaining stable product identities and reviews. Track each import's status and counts, prevent concurrent or out-of-order runs from overwriting newer snapshots, and use export IDs and idempotent writes to make retries safe. Keep the last successful catalogue available when validation or application fails. AWS recommends validation, idempotency and error handling for data pipelines ([AWS ETL guidance](https://aws.amazon.com/what-is/etl-pipeline/)).
5. Persist import results and issue details for a future authorized Product Finder admin interface: last success, export age, failures, warnings and affected SKUs. Notify the agreed PIM and application owners, potentially by email, on failures, missed deadlines or serious data-quality issues; prevent repeated alerts from becoming noise. Define ownership, escalation and reprocessing with those teams. Do not expose internal diagnostics to customers by default.

Open questions include how source order and authoritative corrections are established, whether absence really means unavailable, what row-count or change thresholds are acceptable, and who owns remediation. The proposed take-home duplicate fallback is an explicit temporary assumption, not a substitute for a PIM data contract.
