# Architectural review - LLM generated

This milestone turns the framework skeleton into a working path from a PIM export to a searchable catalogue. The architectural question is where responsibility changes hands: which source we trust, which changes must happen together, and which state needs to survive a reload. Product details and reviews are still ahead of us.

## One application, two ways into the data

Angular owns the customer experience; NestJS owns the read API; PostgreSQL holds the catalogue. A separate manual import script is the catalogue's write path. Keeping the importer outside the HTTP API makes its authority explicit: running it requires database access, while browsing does not grant permission to change products.

These live in one npm-workspace repository, with one dependency lockfile, but remain separate processes. The browser calls `/api` on its own origin through the development or Nginx proxy. That keeps deployment addresses out of frontend code. PostgreSQL also runs locally, so development, migrations and integration tests use the same database behavior.

## The first trust boundary is the export

We assume each CSV is the complete catalogue. This is the most consequential assumption in the slice: an omitted product becomes unavailable. We retain its record and original source status, recording absence separately. That lets the UI say “Unavailable” for a historical product. The exact strategy here, including pruning of old and superseeded items remains to be discussed as one of the topics of productising.

The parser validates the whole file before any database changes. Structural errors and missing SKUs reject the import. Recoverable field problems preserve the product: an unknown status becomes `UNKNOWN`, and an invalid year becomes `null`, with diagnostics. Four-digit years and exactly the known CSV headers are current contract assumptions, rather than guarantees supplied by the PIM.

Conflicting duplicate SKUs select one whole row, using the more pessimistic status and then the later row on a tie. We avoid assembling a product from contradictory rows. The warning makes that compromise visible; it cannot establish which row is correct. A plausible but incomplete export can still pass validation. Production needs an agreed completeness signal and export identity, described in the [PIM follow-up](../../agent/nightly-pim-imports.md).

## Publishing a catalogue is one database change

The migration introduces the product table, source-status enum, unique SKU and timestamps. SKU is normalized to uppercase by the importer; the database enforces uniqueness of the stored value. Existing product IDs survive re-imports. Products are updated or marked absent rather than deleted, preparing for reviews to refer to stable identities. Review preservation still needs verification once reviews exist.

Import application stages the normalized products in a temporary table and updates the catalogue in one transaction. A table lock serializes imports while allowing ordinary reads. Readers therefore do not see a half-applied export. The lock prevents simultaneous writers from interleaving; it does not prevent someone importing an older export after a newer one.

The timestamps answer different questions:

- `createdAt`: when the product first entered this database.
- `updatedAt`: when its stored content or presence last changed.
- `lastImportedAt`: when an accepted import last contained it.

An unchanged re-import advances only the last-imported time. These semantics are maintained explicitly by the import SQL; PostgreSQL does not automatically provide them. Migration and seeding are separate steps: creating the schema does not publish product data.

The diagnostic file is written after the transaction commits. If writing it fails, the script reports failure and explicitly says the database import has already completed. Database publication and filesystem logging are separate operations, so an unsuccessful command does not always mean unchanged data.

## The API owns the meaning of a query

The browser submits search, filters, sort and a bounded offset. The API validates these independently of frontend controls, applies availability rules, and returns product summaries, a total, a continuation offset and application-area options. Search is literal, case-insensitive matching on name/SKU; multiple values within a filter use OR, while filter groups use AND.

Queries bind customer input as parameters. Name ordering uses SQL to compare lowercase names, put missing names last and break ties by SKU. Counting uses Prisma filters. This gives us the required ordering, but leaves two representations of matching logic that future changes must keep aligned. Frontend and API types are also maintained separately; integration tests currently check their agreement.

The API has no authentication in this assignment. Its public boundary is read-only today; that does not settle validation or abuse controls for the future review write flow. Internal database errors are not returned to customers.

## The browser separates intent from work in progress

The URL represents committed search, filters and sort. Reload, sharing and browser navigation restore those criteria. Typed text and drawer selections are drafts: desktop search commits on Enter or blur, mobile search on confirmation, and drawer edits on Apply. Closing a drawer discards its changes. Sharing restores the query, not the exact scroll position or loaded batches.

The implementation currently keeps routing, drafts, HTTP coordination and loading state in the root Angular component. This is compact for one screen, but more concentrated than the planned page/state/API separation. Extracting those responsibilities is a useful review topic before details and reviews add more transitions.

Changing criteria cancels the old request, resets accumulated results and advances a generation counter so an obsolete response cannot populate the new view. Automatic scroll loading and the manual button share the same loading guard. A failed next batch preserves existing products and waits for explicit retry; successful retry restores automatic continuation.

## Where consistency stops

Stable ordering makes offset traversal predictable while the data stays unchanged. An import between batches can shift positions, causing omissions or repeats. Even one API response reads items, count and filter options through separate queries, so those values need not describe the same database snapshot during an import.

This is an accepted limitation of the current implementation, rather than a solved concurrency contract. Snapshot-aware browsing or cursor pagination deserves evaluation alongside indexing and representative performance measurements. Passing functional tests does not establish the challenge's catalogue-scale performance.

The [agent development log](../../agent/dev.log.md) holds detailed implementation and verification evidence; [DECISIONS.md](../../../DECISIONS.md) records the wider trade-offs and open assumptions. This document is a starting point for our architectural review, not a claim that the remaining risks have been resolved.
