# Architectural review - LLM generated

This slice extends the catalogue into product inspection, sharing and return navigation. It introduces a read path across the existing Angular, NestJS and PostgreSQL application; it does not add a product write path or reviews. The [v0.1.0 review](../v0.1.0/v0.1.0.md) covers the import and catalogue foundation.

## Product identity and the read boundary

Each product has a dedicated `/products/:id` route backed by `GET /api/products/:id`. The API retrieves the product independently of catalogue filters and returns customer-facing fields, together with the status and presence information needed to explain availability. Invalid or missing identities produce a not-found response; infrastructure failures remain service errors. Database and import timestamps are not exposed as product details.

The route uses the existing product UUID. Imports match on normalized SKU and preserve the ID for a continuing or returning product, so links survive ordinary re-imports. A fresh database rebuild generates new IDs, and a changed SKU is treated as a different product. This is an explicit limitation of the chosen identity: stable links across database rebuilds would require a different identity strategy. SKU-based URLs were an alternative, with their own encoding and SKU-change questions.

Products absent from the latest import remain accessible by direct link, but are shown as unavailable with an explanation. Unknown source status is also unavailable, without claiming stock or orderability. The detail view handles incomplete records with explicit missing-value text; an empty certifications list does not imply that a product is uncertified. Availability presentation is shared with catalogue behavior so the two views do not independently define status meanings.

## Links carry intent, not a snapshot

The catalogue URL represents applied search, filters and sort. Product links can carry those criteria so that **Back to catalogue** can reconstruct the search, including when the link is opened in a fresh session. The product lookup itself does not depend on the criteria, so the product remains visible even if it no longer matches them. A direct product link without criteria returns to the default catalogue.

The return fetches current results from the top. Draft edits, loaded batches and scroll position are not part of the link, and a shared URL does not promise a historical snapshot. Browser Back follows browser history; the explicit return link has a deterministic catalogue destination. Criteria parsing and serialization are shared across the views, with invalid values handled through defaults and a warning.

## Sharing and recovery belong to the interface

The catalogue and product views use a shared controller for native sharing when supported and copying a link. Cancellation of native sharing is normal; clipboard failure exposes a manually selectable link. Feedback can be dismissed, with focus returned to the copy control. Only committed catalogue criteria enter shared links.

The detail page owns loading, missing-product and service-error states. It clears prior product content when the route changes, preventing a failed or delayed request from presenting stale details as the requested product. Not-found and service-error states provide a route back to the catalogue; service errors also offer retry. Focus and responsive layout are part of the navigation behavior, including on mobile.

## Boundaries and next decisions

A dedicated page was chosen over a modal, giving product details their own shareable route. The existing incremental catalogue loading remains; restoring scroll position or loaded batches was deliberately left out. UUID links are durable only for the lifetime of the retained database. Reviews and ratings, their persistence and public write protections remain future work. Catalogue-scale performance and consistency across an import during browsing also remain open questions from the previous slice.

The [slice plan](../../agent/product-details/product-details-plan.md) records agreed behavior and review evidence, while [DECISIONS.md](../../../DECISIONS.md) records wider trade-offs. The slice has been human-reviewed; the screenshots below document the implemented interface, not new acceptance evidence.
