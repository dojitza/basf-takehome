# Decisions

## Scope and status

The human approved a buildable, runnable foundation before product features. This phase wires the required technologies and verification tooling. The catalogue snapshot import and product migration are implemented; catalogue browsing is implemented; product details and reviews remain future work. Technical checks do not imply human acceptance or completion of the assignment.

## Architecture

One npm-workspace repository contains an Angular application (`apps/web`) and a NestJS API (`apps/api`). PostgreSQL is accessed through Prisma. The frontend uses standalone components, routing, SCSS and PrimeNG Community. Docker Compose runs PostgreSQL, the API and an Nginx web container. In containers, Nginx serves the production Angular build and proxies `/api`; Angular's local development proxy uses the same API path.

Local development uses the same PostgreSQL engine in Compose and runs both application watchers on the host. `npm run dev` starts and waits for the database; its volume persists after the watchers stop. Integration tests use a separate disposable PostgreSQL container. SQLite would remove the Docker dependency, but Prisma migrations are provider-specific and a second database would introduce divergence and maintenance for a PostgreSQL assignment.

The framework, database, ORM, styling, test runner and Docker requirements are supplied constraints. The choices below concern how we connect them.

## Angular and PrimeNG compatibility and licensing

Keep Angular 22 and PrimeNG 22 together: the assignment requires the latest stable Angular and PrimeNG, and the current PrimeNG 22 peer dependencies support Angular 22. PrimeNG 21 is MIT-licensed and avoids the Community key, but declares Angular 21 peer dependencies; using it with Angular 22 would introduce an unsupported compatibility combination. PrimeNG 22.1.4 is pinned in the frontend package; the lockfile records the installed Angular 22 versions.

**Licensing risk:** PrimeNG 22 requires a license key, including for the Community offering. Confirm whether the relevant company already holds a suitable license; if not, reevaluate the dependency and licensing options before organizational use. Company licensing and eligibility have not been verified. The human selected Community for this take-home and will supply a key. No Pro components are used. An ignored local TypeScript configuration is initialized with an empty value and passed to PrimeNG's documented `license` option. A real key can be added without a tracked change; it is client-visible after compilation. Missing-key behavior remains intact. A valid key has not yet been verified.

## Testing and delivery

Jest is configured in both applications. Focused checks cover shell/PrimeNG rendering, environment validation, generic database-failure behavior and HTTP readiness against real PostgreSQL. Production builds exercise the frontend/backend compiler toolchains. ESLint includes Angular template/accessibility rules; Prettier provides consistent formatting. CI reuses the root commands and adds Compose startup and an integration test. Local evidence is recorded in the agent development log; hosted CI has not been observed yet.

## Deferred decisions and risks

- **Catalogue import:** Treat each CSV as the complete PIM catalogue; assume products absent from a later snapshot are no longer available, and retain their data and future reviews while marking their absence. Confirm export completeness and absence/discontinuation semantics with the PM. Use case-insensitive SKU identity (the sample provides no evidence about whether case is significant); confirm PIM identity rules with the PM. Trim text, preserve other spelling, split and trim pipe-delimited certifications, and treat empty certifications as an empty list. Treat an empty launch year and `n/a` as unknown. Preserve products with a missing name and report them; confirm expectations with the PM/customer and revisit display behavior when designing the UI.
- Normalize observed status variants; import unrecognized statuses as `UNKNOWN` with a warning and treat them as unavailable in the eventual UI. Treat malformed launch years as unknown with a warning; this implementation accepts four-digit years. The seed requires exactly the known CSV headers, an assumption to confirm with the PIM owner. For duplicate IDs choose the whole row with the most pessimistic status, ordered `UNKNOWN`, `DISCONTINUED`, `PHASE_OUT`, `ACTIVE`; for a tie, choose the later row. Prominently report conflicts and selected values in the seed output. Keep the seed manual for the take-home. Reject unreadable, empty or structurally invalid files and rows missing SKU before applying changes. A nonempty partial export cannot be reliably detected from the sample alone.
- The manual seed uses a maintained CSV parser, validates before opening its transaction and applies each snapshot with set-based SQL through Prisma. A database lock serializes imports. PostgreSQL timestamps use timezone-aware instants.
- Track `createdAt`, `updatedAt` (including presence changes), and `lastImportedAt` (most recent successful snapshot containing the product); an unchanged re-import only advances the last-imported time. The catalogue displays absent products as unavailable, keeps discontinued and phase-out distinct, and identifies unnamed products by SKU.
- **Production follow-up:** Agree a versioned full-export contract and ownership with the PIM team, including delivery schedule, completeness, identity, status meanings and validation. Automatically receive and validate nightly exports, apply accepted snapshots atomically and idempotently, and retain the last successful catalogue on failure. Record import results and data-quality issues for an authorized Product Finder admin interface, with possible email alerts to responsible owners for failures, missed exports and serious conflicts. These are future proposals, not take-home features; see [nightly PIM imports](docs/agent/nightly-pim-imports.md) for details and open questions.
- Repeated imports must preserve reviews. Verify this with an integration test when the review model is implemented; bootstrap database connectivity does not verify that future guarantee.
- **Catalogue browsing:** Search name/SKU, filter by status and application area, sort by name and load further results automatically with an accessible fallback. The human agreed that unavailable combines unknown and absent products while discontinued remains distinct, and that catalogue criteria are shareable in the URL. Desktop searches apply on Enter or leaving the field; mobile searches require confirmation. See the [browsing plan](docs/agent/catalogue-browsing-plan.md) for agreed behavior and implementation details and remaining scale questions.
- Review fields, ratings and public submission validation are undecided. Authentication and moderation workflows are excluded by the assignment.
- The initial container setup is for local evaluation. Production would require environment-specific credentials, TLS, deployment/migration policy and operational controls selected for the actual hosting environment.
- Dependency audit at bootstrap reports no runtime vulnerabilities (`npm audit --omit=dev`); the full development tree reports 39 low/moderate findings propagated through test-tool dependencies (deepmerge, glob and minimatch). No forced major downgrade or unverified override was applied. Revisit as upstream fixes become available.
- No shared contract package, generic repository abstraction, auth scaffolding, background scheduler or feature modules have been added without an immediate need. Domain contracts and module boundaries will follow agreed behavior.

The browsing API uses bounded offset batches (30 by default, maximum 100), a total count and a stable name/SKU order. Offset pagination is simple for this catalogue but concurrent imports can shift later batches; cursor or snapshot semantics and indexing need evaluation against the expected 50,000-product scale. Application-area options come from distinct imported data. The interface uses PrimeNG controls alongside native form controls and a small responsive drawer; product rows are not links until detail pages exist.

For the take-home UI, the supplied dark-blue BASF raster lockup is converted from its embedded CMYK profile to sRGB PNG for consistent browser display; the lockup itself is unchanged. Confirm identity permission and an appropriate digital master before use beyond this exercise. Status tags retain text labels and use neutral, pale yellow and pale red styling for active, phase-out and discontinued; absence remains unavailable.
